# CI and automatic releases

The workflows take effect after they are committed and pushed to `main`.
Creating Actions secrets alone does not run CI or publish a release.

## Checks

[`ci.yml`](../.github/workflows/ci.yml) runs on pull requests targeting `main`
and pushes to `main`, with read-only repository permissions:

- Rust formatting, tests, and Clippy.
- Release eligibility checks with a mocked GitHub CLI, including retries and
  rejected direct pushes, outdated commits, and mismatched drafts.
- ARM64 JNI build for Haval and x86-64 JNI build for emulator tests.
- An unsigned, R8-optimized release build and release lint.
- Android regression tests on an API 28 x86-64 emulator.

Reports are retained as Actions artifacts for seven days. The CI workflow does
not reference signing secrets. Third-party actions are pinned to commit hashes.

To check workflow edits locally, run `actionlint` and
`python3 .github/tests/test_release.py` (Python 3, Bash, and `jq` required).
The latter makes no network requests and publishes nothing.

## Releases after merge

[`release.yml`](../.github/workflows/release.yml) waits for successful CI on
`main`. It publishes only when the checked commit is still the head of `main`
and is associated with a merged pull request. PR checks, direct pushes, failed
checks, and superseded commits do not publish releases.

The workflow checks out that exact commit, rebuilds the ARM64-only Haval release,
signs it with the release key, verifies the signature, and prepares a draft
GitHub Release with:

- `impulsefy.apk` — signed Android package.
- `impulsefy.apk.sha256` — SHA-256 checksum for the download.
- A changelog generated by GitHub from the changes since the previous release.

The draft is published after the assets upload. A retry can resume its draft;
an already published release is skipped. The workflow checks the current `main`
commit again before publishing, so an older build does not replace a newer one.

Versions use `0.1.N`, where `N` is the triggering CI run number; tags use
`v0.1.N`, and Android `versionCode` is `N + 1`. Gaps are expected because PR
checks also consume CI run numbers. Keep this numbering monotonic when changing
the release scheme. Gradle accepts `-PappVersionName` and `-PappVersionCode`;
local builds default to `0.1.0` and code `1`.

## Signing secrets

Repository Actions secrets are configured in
[paulovitin/impulsefy settings](https://github.com/paulovitin/impulsefy/settings/secrets/actions):

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | Base64-encoded private release keystore |
| `ANDROID_KEYSTORE_PASSWORD` | Keystore password |
| `ANDROID_KEY_ALIAS` | Signing key alias |
| `ANDROID_KEY_PASSWORD` | Signing key password |

The signing step decodes the keystore into the runner's temporary directory and
removes it on exit. Passwords are passed to `apksigner` through environment
variables. Never commit the keystore, passwords, or their Base64 encoding.
Keep a private backup outside the repository: future updates require the same
signing key. GitHub does not provide a way to retrieve a saved secret's plaintext.

The release certificate differs from the local development certificate. Android
cannot install it as an update over a development-signed APK; switching from that
build requires uninstalling it and pairing again. Subsequent releases signed
with the same release key can update each other.

The build scripts still support local development signing through
`./scripts/build-apk.sh`; the release workflow uses `apksigner` separately and
never publishes a development-signed APK.
